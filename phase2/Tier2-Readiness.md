## 7. Stream-builder architecture (built 2026-09-22)

`src/tier2_module/`:
- `config.py` — `Tier2StreamConfig`: column names and window size (500 cases).
- `real_model.py` — `RealDeployedModel`: logistic regression, frozen after fitting, threshold set to hit the target sensitivity on its own training labels (same rule as Tier 1's `DeployedModel`, so real and synthetic models are held to the same standard — no tuning to favor any monitoring arm).
- `windowing.py` — `assign_windows`: sorts by calendar order, drops the remainder that doesn't fill a whole window.
- `stream.py` — `build_stream_data`: assembles a `StreamData` (the exact shape `src.monitor_module` and `src.eval_module` already consume for Tier 1). Severity is drawn from the same elicited class-conditional distribution as Tier 1 (`draw_severity_from_probs`, factored out of `SyntheticWorld` for reuse) — **a modeling choice, not a data fact**: no real case carries a clinician severity label, so severity is assigned stochastically from the elicited weights, conditioned only on whether the case was a true event.
- `synthetic_stand_in.py` — schema-matched fake cohort generator, used for every test and for `scripts/m7_tier2_demo.py`.

`scripts/tier2_extract_features.py` — real MIMIC-IV extraction (vitals/labs over the first 24h, aggregated mean/min/max/last/count; sepsis via Sepsis-3 (`mimic_derived.sepsis3`) per D8, readmission, mortality, on `paper2_stays`). **Written for you to run on your machine; I have not run it and will not run it against the live database.** The output (order key, label, subgroup, 115 feature columns) never carries `hadm_id`/`subject_id`/`stay_id` — those are used only internally to join tables and are dropped before the file is written — but it does carry real vitals and labs, so use your own judgment about what you share with me. Item IDs reused from the Deferral Frontier paper's own MIMIC-III script (MetaVision-era IDs, which MIMIC-IV also uses) — not independently verified against `mimic_icu.d_items` in your instance; worth a spot check.

`src/tier2_module/perturb.py` — three **input-only** perturbations, decided 2026-09-22 as the first slice of §3 (they act only on model inputs or the model itself, never on a real case's label, so they never override a real outcome — unlike SC08/SC19, deferred):
- `rescale_and_rescore` (SC07): multiplies a feature column by a ramped ratio from a given onset window, then rescores.
- `missingness_and_rescore` (SC05/SC06): masks a feature column at a ramped probability, imputed with the training mean, then rescores.
- `version_regression_and_rescore` (SC17): swaps in a `RealDeployedModel.with_regression` copy (weight vector partially replaced by an orthogonal direction) from the onset window, then rescores.

All three reuse `progress_schedule` from Tier 1 directly, so an onset window `s0` and a shape ("abrupt"/"gradual"/"incremental") mean the same thing in both tiers. `RealDeployedModel` gained `impute_means` and `with_regression` to support them, mirroring Tier 1's `DeployedModel`.

**Deferred, needs its own design pass:** SC08 (concept drift) and SC19 (scope creep) — injecting them onto a fixed, already-observed real cohort would mean synthetically overriding some real outcomes or the real invocation population, which is a scientific-integrity decision, not an engineering one. Real drift already shows up naturally in the mortality series (§6) as a partial alternative.

`src/tier2_module/resample.py` — `block_bootstrap_windows`/`block_bootstrap_stream`: resamples `n_windows_out` windows from a real (or synthetic stand-in) cohort in contiguous blocks of `block_size` real windows, each block's start drawn independently with replacement. This is the piece §3 called for ("the same false-alarm calibration on real null streams, since real windows are not exchangeable" and "replicates are resamples of one dataset") — it produces many null-stream replicates from the one real dataset for false-alarm calibration, preserving real within-block serial structure while still giving independent-ish replicates across blocks.

**Drift/onset confound: fixed (2026-09-22), with a caveat.** `tier2_onset_index_rolling` replaces the fixed early-period baseline with a rolling one, computed from the `n_lookback` real windows immediately preceding each monitored window, so a naturally drifting real series (like Sepsis-3's) doesn't get compared against a stale reference. It shares the exact same onset-crossing logic as the fixed variant (`_crosses_onset`, including the zero-baseline handling above), so the two are directly comparable. Trade-off, the same kind Tier 1's rolling-calibration sensitivity study already found for the detection threshold (`M5f-Rolling-Calibration.md`): a rolling reference can partly absorb a persistent rise into itself, weakening detection of a genuine, sustained failure; an abrupt step is unaffected, since the windows just before it are still a clean reference.

**Honest empirical finding, not yet resolved:** the demo (`scripts/m7_tier2_demo.py`) tests this on a synthetic declining-prevalence stream with **no injected perturbation** — drift alone, at roughly 1.3%/window. The fixed baseline falsely triggers "onset" at window 3, as expected. The rolling baseline (lookback 4) still falsely triggers, at window 1 — the demo's drift rate is deliberately steep to make the confound visible quickly, but it is also about **11× steeper than the real Sepsis-3 series** (~0.12%/window, 48.4% to 34.9% over roughly 114 real windows, §6). So whether a short lookback fully absorbs the *real* drift rate is not yet confirmed — it needs checking against the real data's actual pace once extracted, and the lookback length (currently a bare parameter with no default recommendation) needs tuning to that real pace rather than an arbitrary choice. Reported as-is rather than tuned to look clean.

## 10. The C-component 200.0 ceiling: root cause, fix, and how it changed §9's numbers (2026-09-24)

You asked me to look into the C-ceiling left open in §9. Diagnosis, root cause, and fix below — and re-running everything affected by it, since (unlike a self-contained bug) this one turned out to be silently suppressing real signal in the arms sharing a threshold with it.

**Diagnosis.** `calibrate_threshold`'s search range is `[0.2, 200.0]` (`src/monitor_module/detectors.py`). Checking whether 200.0 was a genuine floor or just an insufficient search range: the C group's null-stream alert rate kept dropping well past it (16.8/1,000 at h=200, down to 8.75 at h=1,000, 4.3 at h=10,000, 0 at h=1,000,000) — so the range was simply too narrow, not a hard limit. Why C2 needs such an enormous threshold: `C2 = K * sum_k (window_mean_x_model[k] - mean_ref[k])^2` (`src/monitor_module/statistics.py`) sums **unweighted** squared per-feature deviations across all `K` model features. On Tier 1's synthetic world every feature is unit-scale by construction (`rng.standard_normal(...)`), so this is a reasonable multivariate drift statistic. On real MIMIC-IV data, feature natural scales range from SD 0.5 to SD 31,500 — a 60,000x ratio — and checking the worst offenders' aggregate percentiles (no row-level values inspected) showed why: `vital_nibp_mean_max` has a clinically plausible 99.9th percentile of 227 but a raw maximum of 8,999,090; similarly for `vital_resp_rate_max` (max 7,000,400), `lab_lactate_max` (1,276,103), `vital_nibp_sys_max` (1,025,100) — almost certainly MIMIC-IV chart-error artifacts (well under 0.1% of rows per column: 11-62 out of 76,000-83,000). Squaring in C2 amplifies these enormously; the ratio/AUROC-based P/U indicators are naturally immune.

**Fix (your choice: "clip and re-verify," percentile-based winsorization rather than a hand-picked clinical bound per feature or a log transform).** `RealDeployedModel` now winsorizes each feature at the 0.1st/99.9th percentile fit on the training cohort only (no leakage, same discipline as `impute_means`/`StandardScaler`), applied in both `fit` and `apply` before imputation. Percentile-based, not a clinically-asserted bound, because the diagnostic already showed genuine extreme-but-real values (lactate 20, NIBP 227) sit comfortably inside the 99.9th percentile while the errors sit far beyond it — an objective cutoff, not 115 hand-picked ranges. `impute_means` is now also computed post-winsorization, so the handful of extreme rows can't skew the value used to fill missing data either. TDD'd (4 new tests), 3/3 mutants killed, including a real bug the tests caught: an all-missing training column made `nanpercentile` return NaN bounds, and `np.clip` with NaN bounds silently turns **every** value in that column to NaN on any future cohort scored — not just the all-missing training case — corrupting genuine, valid real data. Fixed with a no-op `(-inf, inf)` fallback, matching `impute_means`' own 0.0 fallback for the identical edge case.

**Confirmed fixed:** the C group's threshold is now ~9-17 across all three tasks (sepsis 12.13/16.86, mortality 12.30/16.77, readmission 11.99/17.93 for split/tilted), never 200.0.

**But this was not a self-contained fix — C2's broken scale was silently poisoning every arm that shares a CUSUM threshold with it (union, label-free), the same mechanism as the readmission U3 anomaly (§8): one indicator's astronomically heavy tail forces the whole shared threshold up to avoid false-alarming on it, which then silences every other indicator sharing that threshold too. Only the arms that give C its own separate threshold (component-split, tilted) were insulated. This is exactly why §9's result read as "the advantage is concentrated in the C-component specifically" — that reading was itself an artifact of the bug just fixed, not a real mechanistic finding.**
